# 版本完整性与生产发布规范

本规范解决一个已经实际发生的问题：下载页显示了新版本，但数据库更新策略或生命周期接口仍返回旧版本。版本发布不是“上传一个网页”，而是一个不可拆分的发布单元。

## 唯一发布单元

一次 Android 发布必须同时绑定以下内容：

1. 源码提交、`versionName` 与单调递增的 `versionCode`。
2. 四端包名、构建类型、签名证书指纹、APK 文件名、大小与 SHA-256。
3. 下载站页面和 `release-metadata.json`。
4. 服务器版本目录中的四个 APK。
5. 数据库 `software_update_policies` 中四端生效策略。
6. `/api/public/lifecycle` 对四种 edition 返回的更新信息。
7. 数据库备份、静态站备份、发布时间和操作审计。

任意一项不一致，整次发布都应判定失败，不能对外宣布完成。

## 原子发布流程

发布状态机固定为：

`构建 -> 本地制品校验 -> 服务器暂存 -> 数据库备份 -> 策略事务 -> 公网制品回读 -> 四端生命周期核验 -> 正式生效`

推荐命令入口：

- `backend/tools/publish-android-ssh.py`：上传或复用经过哈希验证的制品，备份数据库并同步四端策略。
- `backend/tools/verify-production-release-ssh.py`：验证四端生命周期响应，并回读公网 APK 的 MIME、长度和 ZIP 文件头。
- `download-site/scripts/deploy-static.py`：只负责静态页面与制品目录，不能单独代表完整 Android 发布。

发布失败时必须一起回滚下载页、APK 目录、数据库策略和更新接口状态，不能只恢复其中一项。

## 发布台账

每次发布至少保存以下字段：

| 类别 | 必填字段 |
| --- | --- |
| 源码 | Git commit、分支、构建时间、构建环境 |
| 版本 | versionName、versionCode、edition、packageName |
| 签名 | 证书 SHA-256 指纹、签名方案、是否可覆盖安装 |
| 制品 | 文件名、字节数、SHA-256、公开 URL |
| 数据库 | 四端策略 ID、生效范围、forceUpdate、备份路径 |
| 验证 | 生命周期 4/4、公网 MIME、Content-Length、ZIP 文件头、真机安装结果 |
| 运维 | 操作者、发布时间、静态站备份、数据库备份、回滚结果 |

## 缓存与下载安全

- 下载页和生命周期接口使用 `no-cache` 或短缓存，并带 ETag，避免客户端长期看到旧版本。
- 带版本号的 APK URL 可使用不可变长缓存，但同一 URL 对应的文件内容绝不能被替换。
- APK 响应必须是 `application/vnd.android.package-archive`，支持 Range，长度与发布清单一致。
- 公网回读的前四字节必须是 ZIP/APK 文件头 `PK\x03\x04`，不得返回 Nginx/PHP HTML 错误页。
- 客户端安装前再次核对包名、versionCode、签名证书和 SHA-256。

## 回滚与清理

- 数据库迁移前执行备份，并定期进行恢复演练；“有备份文件”不等于“可以恢复”。
- 保留上一稳定版 APK、策略快照和站点归档，记录明确的回滚命令。
- 暂存目录使用发布 ID 命名，成功后删除；异常中断的暂存目录移入备份区并记录，不直接无审计删除。
- 禁止复用 `versionCode`；回滚时应发布更高 versionCode 的修复包，避免 Android 降级限制。

## 当前发现但仍需处理的风险

这些是发布核验中补充发现的内容，不应被误写为已经完成：

1. **生产仍使用 debug 制品**：必须迁移到固定 release 签名，记录证书指纹，并在至少两代版本间验证覆盖升级。
2. **历史凭据曾进入沟通记录**：必须轮换 SSH、面板、数据库及 API 凭据，改用密钥登录、最小权限账号和 CI Secret。
3. **公网仍使用 HTTP 链接**：应启用 HTTPS、HSTS 和可信证书，防止更新包与元数据被劫持。
4. **缺少灰度与暂停能力**：应按 edition、应用、用户比例和设备条件分阶段放量，异常时可暂停而不必重发包。
5. **缺少安装结果遥测**：客户端应脱敏上报下载失败、哈希失败、签名冲突、解析失败和安装结果。
6. **缺少真机安装门禁**：至少覆盖小米、vivo、OPPO、华为和原生 Android 的下载、覆盖安装和回滚恢复。
7. **缺少可复现构建证据**：应锁定 JDK/Gradle/Android SDK/依赖版本，生成 SBOM 并记录构建环境摘要。
8. **源码存在历史编码债务**：发布前应执行 UTF-8/乱码扫描，防止用户界面再次出现不可读字符。
9. **缺少版本一致性 CI 门禁**：任何源码、APK、元数据、数据库策略或生命周期响应不一致都应让流水线失败。
10. **缺少灾难恢复演练**：需定义 RPO/RTO，验证数据库、媒体和更新制品能够从异机恢复。

## 完成标准

发布只有在四端生命周期核验 4/4、公网 APK 回读、签名连续性、真机安装、备份可恢复和监控无异常后才算完成。修改页面文字、缓存刷新或上传单个 APK 都不算完成发布。
