# 外部参考学习与易运盈吸收结论（2026-08-20）

> 目的：学习用户指定的开放平台、卡密后台、文件上传与共享对照页的功能组织和实现思路，提炼可验证的产品闭环；不复制第三方代码、品牌、凭据或不安全做法。
> 项目边界：官方托管唯一公开 API 身份是 `https://appht.jjmxg.xyz/`；源码买断自建必须使用购买方自己的 server、KEY、数据库、包名/签名与更新通道。
> 证据边界：本文记录 2026-08-20 的公开只读快照与本地测试。第三方页面、路由目录或本地实现均不能单独证明生产环境已经开通或真机通过。

## 2. 对汇云公开接口的功能与实现逻辑理解

本轮通过公开目录 API `https://api.huiyuns.cn/app/doc/list` 递归统计到 **71 条唯一接口**，其中 GET 37、POST 34。目录顶层包括新手指引、文件上传、公告通知、版本更新、卡密、用户、论坛、订单/支付、角色权限和数据统计；实际有文档接口的业务分组覆盖上传、公告、版本、卡密、用户资料/登录/资产/日志/关注、论坛板块/帖子/评论/打赏、套餐/订单/支付及论坛管理审核。

### 2.1 身份链

公开文档把身份大致分为两层：

1. `hid + secret` 表示项目/应用身份；
2. 登录后再携带 `token` 表示用户身份；
3. 管理范围另有 `/manage/` 路由族。

这种“应用归属 + 登录主体”的两段式思路值得吸收，但不能照搬静态 Secret 直接下发客户端。易运盈继续采用：

- 官方托管由 `X-App-Key/app_key` 识别应用，它是可公开的应用唯一标识，不冒充服务器秘密；
- Bearer Token 绑定用户、应用、上级和有效期，服务端再次检查租户与权限；
- `app_secret`、平台秘密、签名密钥和数据库凭据只留在服务端/受控部署环境；
- 管理员、授权代理和 Level 1 平台总控使用独立登录与权限回读，不依赖前端隐藏菜单。

### 2.2 上传到业务引用的闭环

汇云目录把 `/api/v1/upload` 放在最前，并在用户头像和论坛图片说明中引用上传后得到的文件 ID。这说明上传不是孤立按钮，而是公共基础能力：

```text
选择文件
  -> multipart 上传
  -> 服务端校验类型/体积/归属并返回文件 ID
  -> 列表回读文件、哈希、状态和预览能力
  -> 其他业务只引用服务端 ID
  -> 删除/复用继续做归属与引用检查
```

易运盈本轮已把这一思路落实到公开接入说明：新增并核对 `POST /api/user/uploads` 与 `GET /api/user/uploads`，明确 multipart `file` 字段、`upload_id`、SHA-256、分页、关键词、场景、类别和日期筛选；上传后必须用列表回读，不把前端成功提示当最终状态。服务端路由和 `UploadLibraryService` 原本已存在，本轮没有虚构新生产能力。

### 2.3 卡密闭环

公开目录把卡密拆为三种语义：未登录可验证使用次数、按生效时间验证、登录用户兑换余额/VIP/经验。可吸收的不是接口名称，而是状态机边界：

```text
输入卡号
  -> 校验应用归属/状态/时间窗/次数/设备或用户约束
  -> 原子扣减或绑定
  -> 返回兑换/授权记录 ID
  -> 用户端读取“我的卡密/资产/授权”确认结果
  -> 重复提交必须幂等或明确冲突，不能重复发放
```

易运盈已有卡密兑换、设备绑定、记录与服务端权限校验；仍应把“授权有效是否阻断具体受控功能”作为每个部署的产品配置，而不能只在客户端显示激活成功。

### 2.4 用户、论坛和订单支付闭环

- 用户：注册/登录 -> 回读资料和资产 -> 变更资料/邮箱/密码 -> 日志与消息 -> 退出撤销会话。
- 论坛：板块/帖子列表 -> 详情 -> 发布/编辑/删除 -> 点赞/收藏/评论/打赏 -> 我的内容列表 -> 管理审核。
- 订单：套餐详情 -> 创建订单 -> 取得 `order_id/order_no` -> 发起支付 -> 查询支付详情与状态 -> 回读订单。

这些流程说明“列表、详情、写入、状态回读、我的记录、后台治理”需要同时存在。易运盈的最小闭环也采用这个结构；但当前 Android 统一订单详情/物流/虚拟交付、不可改票 UI 和全入口强制更新仍有明确缺口，不能因参考站有类似目录就宣称完成。

## 3. 值得吸收的文档体验

1. 左侧按业务分组，支持关键词检索，避免在长页面中人工查找。
2. 每条接口同时展示方法、路径、认证类型、请求头、请求参数、响应字段和示例。
3. 用上传 ID 串联头像、论坛等下游业务，让读者知道“下一步怎么用”。
4. 将公开能力与管理能力分组，减少最终用户误用管理接口。
5. 目录由服务端数据生成，便于统计接口数量与发现文档漂移。

易运盈公开文档现已提供 60 条经过仓库路由目录核对的白名单接口、接口搜索、四角色认证矩阵、响应与回读约定、cURL/Java/JavaScript 转换、复制/分享/打印及最小闭环清单；静态导出页也完成了真实输入与清空交互测试，不依赖 React 水合后才可搜索。

## 4. 明确不能照搬的安全与合同缺口

以下是 2026-08-20 公开快照可观察到的边界，只用于提醒易运盈门禁，不对第三方内部实现作推断：

1. 文档要求客户端请求携带 `secret`，但公开资料没有展示 HMAC、nonce、时间戳、签名覆盖字段或重放窗口。长期静态秘密放入 APK/网页会被提取，不能作为最终授权边界。
2. 文件上传表格能识别 `file` 类型并提示 multipart，但页面生成请求示例的代码仍固定写 `Content-Type: application/json`；这类“表格正确、可复制示例错误”的冲突会直接中断新人闭环。
3. 公开成功响应常用 `code/msg/data/list/time`，但没有完整的非成功码、HTTP 状态、限流、冲突、幂等和重试表；调用方难以决定刷新、停止、重读或退避。
4. 列表既可能出现在 `data`，又保留顶层 `list`，若缺少逐接口 schema，客户端容易套错响应结构。
5. 文档未展示写请求的幂等键、订单/兑换防重复语义、上传哈希复用规则或并发状态转换合同。
6. 文档 API 当前返回 `Access-Control-Allow-Origin: *`，允许头只列 `Content-Type, Authorization, X-Requested-With`，与文档中的 `hid/secret/token` 名称不完全一致；响应快照也未见 HSTS、CSP 与 `X-Content-Type-Options`。这不是对整站的全面审计，但足以说明不能照抄其安全响应配置。
7. 未发现多 Base URL、同部署身份握手、只读请求切线、写请求不重放或全部线路失败的公开合同。

因此易运盈坚持：官方包唯一 HTTPS；自建 HTTP 必须 `self_host + allowHttpEndpoints` 二次 opt-in；自动切线只允许 GET/HEAD 的连接类异常和 502/503/504；TLS/证书错误、4xx、普通 500、写请求、上传和 Token 刷新均不跨线路重放，也绝不回退官方服务。

## 5. 本轮已吸收、验证和仍待完成

### 已吸收并有本地证据

- 官方 `hosted` 与买断 `self_host` 双轨；官方只接受 `https://appht.jjmxg.xyz/`，自建拒绝官方域名。
- 自建可配置有序 HTTP/HTTPS 多线路；HTTP 二次确认；连接地址规范化、去重和 fail-closed。
- Android 多线路策略 24/24 定向 JVM/MockWebServer 测试通过；写请求、上传和刷新不重放。
- 公开 API 目录由 58 增至 60，补齐上传与列表浏览；Node 渲染/安全测试 23/23，通过真实静态页面搜索/清空交互。
- 全新隔离 MariaDB + PHP HTTP 的 core/forum/notifications/chat-commerce 四套 smoke 共 185 项通过，并修复排序规则 1267 与维护查询引用不存在列的问题。
- 私有 APK 部署器 28/28、生产权限 hardener 21/21；五处生产 `find` 失败均 fail-closed。
- 生产 STT 模型仅做只读复制与前后哈希回读；权限事务因 FPM/进程前置条件不满足而正确停止，没有把“允许修改”误写成“已安全修改”。

### 仍需单独实现或验收

1. 强制更新覆盖冷启动、登录页、恢复入口和写 API 的统一门禁。
2. Android 订单详情、物流事件与购买者专属虚拟交付。
3. `allow_change=false` 的普通/群投票 UI 禁用与提示一致性。
4. 自建多节点的签名式 deployment identity 握手、恢复首选防抖和全部线路失败 UI。
5. 自建包独立 package/signer/key/data/update channel 的正式构建与真机验收。
6. 官方四端 code66 的安装、升级、登录、数据连续性和系统通知真机证据。
7. 生产 STT/FPM 在满足维护窗口、socket 与进程门禁后再执行权限事务。

## 6. 最终采用原则

学习外部项目时，只吸收可解释、可测试、适合当前原生 Android + PHP/MySQL 技术栈的产品闭环；每项能力必须同时回答：

1. 谁能调用，应用/用户/管理员身份如何绑定；
2. 请求字段和上传格式是什么；
3. 成功返回哪个服务端 ID；
4. 用哪个 GET/详情接口回读最终状态；
5. 401/403/409/422/429/5xx 与超时分别怎么处理；
6. 重试会不会重复扣款、兑换、上传或发消息；
7. 证据属于源码、JVM、隔离集成、真机还是生产；
8. 官方托管与源码买断的服务器、KEY、数据和更新通道是否完全隔离。

不能回答这些问题的“页面存在”“路由存在”“营销描述”或“单次成功提示”，均不作为正式功能闭环通过。
