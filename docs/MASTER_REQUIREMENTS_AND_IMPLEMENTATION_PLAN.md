更新基线：正式首发候选 `1.0.0 (63)`（待新 Build 与 62→63 设备门禁）；线上非强制 Debug 测试版 `2.7.14 (59)`

适用范围：Android 用户端（4）、三级管理端（1/2/3）、PHP API、MySQL、下载站、更新链路与运维平台

## 1. 文档用途与状态规则

本文件把历次需求合并为唯一的产品与工程检查表。它不是“所有需求已经完成”的声明；任何能力只有同时具备客户端、服务端、数据库、权限、异常处理、测试和真实环境验收，才允许标为完成。

状态只使用以下四种：

| 状态 | 含义 |
| --- | --- |
| 已完成 | 已形成端到端闭环，并留有可重复的测试或发布证据 |
| 部分完成 | 已有代码或页面，但仍缺服务端、边界、性能、权限或真机验收 |
| 待实现 | 需求已确认，尚无足够实现证据 |
| 阻塞 | 依赖外部服务、生产凭据、合规确认或用户真机验收 |

每项需求必须具备：需求编号、角色范围、当前状态、实现措施、验收标准、风险和证据链接。页面、按钮、接口占位或静态文案均不能单独算完成。

## 14. 实施顺序

### P0：先保证不会丢数据、不会越权、不会扣错钱

6. `API-001`、`DB-001`：契约、迁移、备份与恢复门禁。

### P1：完成用户高频主路径

1. 相册/文件/媒体/语音/收藏闭环和大文件续传。
2. 资料卡、权限、好友/群选择器和二维码/地图。
3. 动态、论坛、悬赏、投票和评论富媒体闭环。
4. 商店、资源投稿、订单、红包和抽奖类型化 UI。
5. 全局主题、语言、背景、图标、Dock 和底部弹层真机矩阵。

### P2：平台化与智能能力

1. 四级管理端模块继承、策略中心、文档系统和应用市场。
2. 智能机器人检索、天气/新闻工具、本地模型和评测集。
3. 多人通话、美颜、SFU、容量治理和质量监控。
4. 全量可观测性、自动化截图、灰度发布与灾难恢复演练。

## 15. 统一完成定义

任何编号只有同时满足以下条件才可改为“已完成”：

1. 需求、角色、权限和失败路径明确。
2. Android、API、数据库和管理端形成闭环。
3. 用户界面无裸 JSON、服务器地址、堆栈或英文内部枚举泄漏。
4. 有自动化测试覆盖正常、边界、弱网、并发和历史崩溃路径。
5. 小米和 vivo 至少各一台目标设备完成真机截图与交互验收；涉及后台/来电时扩展到 OPPO、华为和原生 Android。
6. 达到性能、安全、隐私、可访问性和数据一致性门槛。
7. 版本、安装包、签名、更新接口、下载站、GitHub、数据库迁移和回滚资料一致。
8. 发布后存在指标、告警、审计和可执行回滚方案。

- 固定顺序为新 A → Stable Build → 62→63 设备门禁 → 证据 B → annotated tag `v1.0.0` → Finalize → 备份/部署/公网回读 → 推送/归档，最终状态只按 finalized manifest 与 Git refs 回读。
